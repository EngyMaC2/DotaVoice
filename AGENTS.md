# Руководство по репозиторию (DotaVoice)

DotaVoice — настольное приложение для голосовой связи в Dota 2: привязывает
командные голосовые каналы к живому матчу через GSI под оркестрацией агента
OpenHands. Есть и сервисный режим (тот же движок без интерфейса).

## Команды

```bash
pip install -e ".[dev,agent,audio]"    # зависимости рантайма, GUI, SDK агента и звука
python -m dota_voice.desktop           # настольное приложение (мастер, окно, оверлей)
python -m dota_voice                   # только сервис (порт по умолчанию 12000)
./install.sh                           # установщик: окружение, зависимости, ярлыки
build_windows.bat                      # Windows: сборка dist/DotaVoice.exe и .msi
python -m pytest -q                    # весь набор тестов
python -m scripts.demo                 # локальное сквозное демо, без сети
python -m scripts.simulate --scenario basic   # отправить GSI-нагрузки в запущенный мост
python -m pytest tests/test_net_crypto.py tests/test_net_mesh.py tests/test_voice_p2p.py
python -m pytest tests/test_security.py tests/test_security_api.py
```

Для headless-проверок GUI используйте `QT_QPA_PLATFORM=offscreen` (тесты) или
`xvfb-run` (ручной запуск). Движок можно проверить без интерфейса:
`python -m dota_voice.desktop --headless-check`.

## Архитектура в одном абзаце

`POST /gsi` принимает JSON от GSI Dota 2. `gsi.parse_gsi` приводит его к
`GameStateUpdate`. `agent.orchestrator.Orchestrator` привязывает его к сессии по
ключу `match_id` через `agent.manager.SessionManager`, затем запускает инструменты
OpenHands (`agent.tools`), которые меняют `VoiceBackend` (`voice/`) и публикуют
события оверлея в `EventBus` (`bus.py`), а `server.py` раздаёт их через
`/ws/overlay`. Настольный слой (`desktop/`) запускает этот движок в фоновом потоке
(`desktop/engine.py`), показывает окно (`desktop/main_window.py`), прозрачный
оверлей (`desktop/overlay_window.py`) и мастер настройки (`desktop/wizard.py`).
`presence.py` подключает само приложение к комнате матча как обычного участника.

## P2P-голос и безопасность

- **`DOTAVOICE_VOICE=p2p`** включает серверлесс-голос (`voice/p2p_backend.py`).
  Сессия — это `MeshSession` (mesh + аудио); каналы логические, «создание канала» =
  запуск mesh. Бэкенд принимает `discovery_factory`, чтобы тесты шли без multicast.
- **`net/` — криптография чистым Python** (XChaCha20-Poly1305, X25519, HChaCha20).
  Сверяйте изменения с официальным тестовым вектором HChaCha20 и с libsodium
  (`pynacl`, зависимость `[dev]`): тесты это делают, не удаляйте их.
- **Изоляция команд — на медиапути**, а не на установке канала. Пир с другой
  стороны просто не связывается (`_on_discovered` отбрасывает его), а
  `broadcast_voice`/`_handle_voice` дополнительно фильтруют по `_peer_teams`.
  Команда пира узнаётся из объявления обнаружения и из управляющего сообщения
  `hello` после рукопожатия.
- **Один канал на пира** (`_dedupe`): пир может быть доступен по нескольким
  адресам (loopback + LAN), и без дедупликации его звук проигрывался бы дважды.
- **Мут локальный и односторонний.** Он ставится на канале (`PeerLink.set_muted`) и
  не влияет на других. Не превращайте его в серверный.
- **Закрытие приложения не равно концу матча.** `P2WlanController.close()` (через
  `P2PVoiceBackend.close`) только отсоединяется от сети (`detach_room`) и оставляет
  карту комнат в файле, а `create_room` для такой комнаты поднимает драйвер заново.
  Комнату удаляет лишь `leave_room` при завершении матча. Если снова начать звать
  `leave_room` из `close()`, чистый перезапуск потеряет комнату и создаст вторую
  сеть для живого матча.
- **`security/policy.py` — источник правды** по VAC- и аккаунт-безопасности
  (никакого чтения памяти, внедрения, автоматизации ввода, паролей Steam; оверлей
  только внешний; мут локальный). Меняете поведение в этих областях — обновите
  инварианты и `docs/security.md`.
- **Steam SDR выключен по умолчанию** и включается только `DOTAVOICE_P2P_STEAM_SDR=1`;
  без этого `SteamSdrTransport` бросает `SdrUnavailable`. Это осознанный риск
  (Steamworks, правила Valve), поэтому не включайте его «за пользователя».
- **Обновления только по подписи.** Манифест проверяется Ed25519, файл — по
  SHA-256, есть минимальная версия и поэтапная раскатка. Никогда не применяйте
  обновление без успешной проверки подписи, даже по HTTPS.
- **Автозапуск только пользовательский** (`HKCU\...\Run`, `~/.config/autostart`,
  `LaunchAgents`) и всегда обратимый; никаких системных каталогов и прав root.

## Соглашения и подводные камни

- **Сессии ключуются по `match_id`.** Никогда не создавайте вторую сессию для уже
  существующего id — в этом весь смысл сервиса. Переиспользование обеспечивается в
  `SessionManager.attach` под блокировкой на каждый матч.
- **Id диалогов детерминированы** (`conversation_id_for_match`), поэтому после
  перезапуска сервис подхватывает тот же сохранённый диалог OpenHands.
- **Исполнители инструментов синхронные.** SDK вызывает `ToolExecutor.__call__`
  напрямую. Асинхронная работа идёт через `MatchSessionRuntime.run_sync`, который
  возвращается на цикл сервиса через `run_coroutine_threadsafe`. Вызовы агента и
  инструментов выполняются через `loop.run_in_executor`, чтобы цикл оставался
  свободным. Не вызывайте `run_sync` из потока цикла — он выбросит исключение, а не
  приведёт к взаимоблокировке.
- **`Conversation` ожидает `uuid.UUID`** для `conversation_id`, а не строку.
  `MatchSession.conversation_id` хранится строкой и преобразуется при подключении.
- **`delete_on_close=False`** у диалогов: состояние сессии должно переживать
  перезапуски.
- **Сохранённый диалог может быть невосстановим.** Если сборка меняет набор
  инструментов, старый `base_state.json` ссылается на исчезнувший инструмент, и SDK
  отказывается его загружать — раньше это валило *каждый* тик GSI с 500, и матч не
  поднимался. `SessionManager._attach_conversation` ловит ошибку, удаляет каталог
  именно этого диалога (`_discard_conversation_state`) и открывает чистый. Голосовая
  сессия живёт в store, а не в истории диалога, поэтому каналы матча не теряются.
- **Регистрация инструментов идемпотентна** (`agent.tools.register_all`), потому
  что каждый новый диалог заново собирает агента.
- **Имена каналов** — `"{метка команды} · {match_id}"`; бэкенд Discord
  переиспользует каналы по этому имени, поэтому перезапуск сервиса не может их
  продублировать.
- **Голосовой ретранслятор** (`voice/relay.py`) создаёт комнату на каждый
  `match_id`; мут и оглушение применяются на сервере, комнаты Света и Тьмы
  изолированы. Аудио для неизвестной комнаты отбрасывается — комнаты создаёт мост
  из состояния игры, а не клиент.
- **Настольное приложение не требует браузера.** Интерфейс общается с движком по
  HTTP на `127.0.0.1`; порт может быть эфемерным (`port=0`), поэтому фактический
  порт читается после привязки сокета.
- **В собранном `--windowed` .exe `sys.stdout`/`sys.stderr` равны `None`.** Из-за
  этого uvicorn по умолчанию падал ещё до привязки сокета: его форматтер логов
  вызывает `sys.stdout.isatty()`. Поэтому `EngineThread` передаёт
  `log_config=None` и логирует сам, а исключение потока движка прокидывается в
  `start()` — иначе пользователь видит только «Движок не запустился вовремя».
  Любой код, трогающий `sys.stdout`/`sys.stderr`, должен выдерживать `None`.
- **Установщик .msi требует `Platform="x64"`** в `<Package>`: компоненты лежат в
  `ProgramFiles64Folder` и помечены `Win64="yes"`, а без этого `light.exe` падает
  с ICE80. Проверяется тестом `test_wix_declares_x64_platform`.
- **Оверлей не должен перехватывать ввод**: у окна выставлены
  `WA_TranslucentBackground` и `WA_TransparentForMouseEvents`.
- **Оверлей рендерится инкрементально, а не через `innerHTML`.** Перезапись
  контейнера состава до десяти раз в секунду перезапускала CSS-анимации и давала
  мигание. `static/overlay.html` строит строки один раз (`ensurePlayerRow`) и далее
  только обновляет их (`updatePlayerRow`); новые строки вставляются в правильное
  место, чтобы порядок не «прыгал». Не возвращайте полный ререндер.
- **`hidden` должен побеждать flex-правила.** Флажки и индикатор речи скрываются
  через `element.hidden = true`, но `.wave { display: inline-flex }` перебивал
  атрибут `hidden`, и скрытые значки оставались видны. Поэтому в `overlay.html`
  есть глобальное правило `[hidden] { display: none !important; }` — без него любой
  новый flex-элемент снова сломает скрытие.
- **Клик-сквозной оверлей не может узнать про `:hover`.** Окно с
  `WA_TransparentForMouseEvents` не получает `mousemove`, поэтому страница не
  обновляет `:hover` и не может сообщить «курсор над кнопкой» — это взаимоблокировка
  окна и страницы, из-за которой перетаскивание «не работало». Поэтому окно само
  читает настоящий курсор (`desktop/pointer.py`) и проверяет попадание по
  прямоугольникам, которые страница отдаёт через `overlayBridge.setInteractiveRects`.
  Каждый прямоугольник помечен действием (`drag` / `mic` / `mute`), и **окно само
  выполняет клик** (`_activate`), а страница при живом мосте клик не обрабатывает —
  иначе он считался бы дважды. Не возвращайте проверку `:hover` из
  `runJavaScript` — она не сработает над игрой.
- **`QWebChannel` надо внедрять, иначе всё молча ломается.** Класса `QWebChannel`
  нет в самой странице: он лежит в ресурсах Qt (`:/qtwebchannel/qwebchannel.js`).
  `desktop/overlay_window.py` читает его и внедряет скриптом на
  `DocumentCreation` в `MainWorld` вместе с бутстрапом, который выставляет
  `window.overlayBridge`. Без этого `typeof QWebChannel === 'undefined'`, шим
  страницы молча ничего не делает, и перестают работать и кнопка микрофона, и
  перетаскивание. Страница обязана читать `window.overlayBridge` **при каждом
  обращении** (хендшейк канала асинхронный и сначала публикует заглушку).
- **Команды игроков, которых нет в GSI.** Обычный (не spectating) клиент шлёт в
  GSI только свой слот, поэтому состав команды из игры не виден. Каждый клиент
  объявляет свою команду через discovery и через `hello` после рукопожатия;
  `VoiceMesh._report_team` отдаёт её один раз на изменение, а
  `MatchSessionRuntime.merge_peer_team` добавляет игрока в состав или доопределяет
  его сторону. Так состав команд и каналы собираются автоматически. Не «исправляйте»
  это, подменяя данные GSI на фиктивные: полный состав доступен только в режиме
  наблюдения.
- **Стороны фиксированы, переводить игроков вручную нельзя.** Разделение на два
  канала существует ровно для изоляции команд, поэтому `move_player` и
  `POST /api/sessions/{id}/move` удалены намеренно, а кнопки «сменить команду» в
  панели и оверлее нет. `MatchSessionRuntime._merge_roster` держит уже известную
  сторону: если GSI пришлёт другую сторону для того же игрока, прежняя остаётся
  (в Dota сторона не меняется по ходу матча — это сбой, а не сигнал). Аналогично
  `merge_peer_team` умеет только *доопределить* игрока, чья сторона была
  `unknown`, но никогда не двигает того, кого уже разместила игра: иначе
  объявление пира пробило бы границу изоляции. Если понадобится «исправить» это,
  сначала вспомните, что две команды не должны слышать друг друга.
- **Состав в оверлее — это «кто в сети», а не только GSI.** `Player.connected`
  отмечает, что приложение игрока на голосовой сети: свой клиент всегда `True`,
  пир становится `True`, когда объявил себя. `Player.connected` — единственный
  источник правды для серого цвета «не в сети». `Roster.unknown` хранит игроков,
  чью сторону игра ещё не сообщила: их видно, но серым. `apply_roster` **сливает**
  входящий состав с уже известным, а не заменяет его, иначе каждый тик GSI у
  обычного игрока выкидывал бы товарищей, добавленных из пиров.
- **Пир может уйти — статус должен вернуться в «не в сети».** `PeerLink.close()`
  шлёт `bye`; `VoiceMesh._handle_control` по нему удаляет связь и зовёт
  `on_peer_left`, а `MatchSessionRuntime.mark_peer_disconnected` снимает
  `connected` и гасит `speaking`. Без этого серый статус оставался бы «в сети»
  навсегда, пока игрок снова не зайдёт. Игрока не удаляем — игра всё ещё его
  показывает, — только меняем флаг.
- **Самомут — жёсткое переопределение.** `MicrophoneController.active` возвращает
  `_active and not _self_muted`, а `set_mode` не сбрасывает самомут. Так кнопка
  «заглушить себя» означает одно и то же в любом режиме. Не меняйте это, иначе
  кнопка будет «пустой» в части режимов.
- **Командный чат повторяет изоляцию голоса.** `chat.py` держит буферы на каждый
  `match_id`; сторону автора определяет `MatchSessionRuntime.post_message` (по
  составу ростера, не по тексту сообщения). Чтение/запись в комнату другой стороны
  отклоняются (`ChatError`), поэтому приватная комната Света никогда не отдаёт
  сообщения Тьме. В mesh-канале `_handle_chat` берёт сторону из `_peer_teams` (что
  мы узнали о пире), а не из поля `team` в сообщении, — иначе пир подделал бы чужой
  канал.
- **Пост-матчевое окно — текст переживает голос.** Матч идёт
  `DRAFT → IN_GAME → POST_GAME → CLOSING → CLOSED` (`match_state.py`); голосовые
  комнаты живут только в `DRAFT`/`IN_GAME`, а текст — ещё и в `POST_GAME`
  (12 минут по умолчанию, `POST_GAME_SECONDS`). Когда матч заканчивается, приватные
  комнаты команд закрываются и открывается общий канал «После матча»: только он
  пересекает границу команд, и только текстом. Окно закрывается по таймеру
  (`SessionManager.reap_stale` → `close_post_game`) или когда вышли все игроки
  (`leave_post_game`). Не открывайте пост-матчевый канал во время матча и не
  оставляйте приватные комнаты после его конца.
- **`end_session` закрывает матч целиком.** `POST /api/sessions/{id}/end` вызывает
  `close_post_game`, а не просто `end`: он завершает и пост-матчевое окно, чтобы
  сессия исчезла из `/api/sessions` (иначе после «Завершить сессию» она висела бы
  ещё 12 минут). Отдельные эндпоинты `post-game/leave` и `post-game/close` —
  для выхода игрока и ручного закрытия окна.
- **Голосовые комнаты живут ровно пока `state.voice_active`.** `ensure_channels` и
  `sync_roster` в `runtime.py` сами отказываются работать вне `DRAFT`/`IN_GAME`,
  потому что их вызывает не только оркестратор, но и `manager.attach` (при
  переподключении) и mesh. Иначе перезапуск приложения в пост-матчевом окне (или
  запоздавший пакет `PLAYING`) создал бы комнаты заново — дубликат канала в
  Discord и голос после конца матча.
- **Автор чата задаётся сервером, не клиентом.** `POST /api/sessions/{id}/chat`
  подставляет `player_id` локального игрока (`runtime.local_player()`), а не
  значение из тела запроса: клиент не может писать от чужого имени. Точно так же
  `GET /api/sessions/{id}/chat` берёт сторону из ростера (`runtime.local_team()`),
  а не из query-параметра — иначе клиент прочитал бы приватную комнату врагов.
- **Панель управления перерисовывает карточки только при смене состава сессий.**
  `render()` в `control.html` сверяет сигнатуру `match_id:phase:reconnects` и при
  совпадении обновляет только блок состава (`.teams`), чтобы ввод чата и позиция
  прокрутки переживали опрос раз в 2 секунды. Не возвращайте полный `innerHTML`
  на каждом тике — это стирает набранный текст.
- Тесты используют подставной ключ LLM, поэтому вызовов LLM не происходит. Discord
  тестируется через подставной HTTP-транспорт — это единственная заглушка в наборе.
  Голосовой ретранслятор и GUI тестируются по-настоящему (реальный UDP, реальный
  Qt в режиме offscreen). Курсор оверлея в тестах подменяется фейковым указателем
  (`FakePointer`), потому что настоящий курсор в CI недоступен.

## Окружение

См. `.env.example`. Для настоящей игры достаточно задать `DOTAVOICE_GSI_TOKEN`
(совпадает с `auth.token` в конфиге GSI); при установке через мастер файл
интеграции создаётся автоматически. GUI требует `PySide6` и системные библиотеки
`libEGL1`, `libxcb-cursor0`, `libxkbcommon-x11-0` (Linux).
